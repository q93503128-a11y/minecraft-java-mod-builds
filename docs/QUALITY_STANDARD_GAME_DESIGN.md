# Minecraft Game Design & Production Quality Extension

이 문서는 `docs/QUALITY_STANDARD.md`의 공용 확장 문서다.

`QUALITY_STANDARD.md`가 UI/UX, 모델, 애니메이션, 코드 구조, 외부 도구, 성능, 자산과 Definition of Done을 다룬다면, 이 문서는 대형 Minecraft 모드를 장기간 개발할 때 자주 무너지는 **게임 설계, 시스템 연결, 작업 운영, 플레이테스트 해석**을 보강한다.

이 문서의 목적은 기능 수를 늘리는 것이 아니라 **실제로 플레이했을 때 하나의 완성된 게임처럼 느껴지는 모드**를 만드는 것이다.

프로젝트 기획서가 더 구체적인 규칙을 정의하면 프로젝트 기획서를 따른다. 단, 공용 품질 수준을 낮추는 근거로 사용하지 않는다.

---

# 1. 기능 구현률보다 게임 완성도

대형 모드는 다음 항목을 별개의 체크박스로 보지 않는다.

- gameplay
- progression
- exploration
- combat
- economy
- UI/UX
- model/texture
- animation
- VFX
- sound
- world design
- performance
- code architecture
- stability

기능이 많아도 서로 연결되지 않으면 완성도가 낮다.

반대로 기능 수가 상대적으로 적어도 각 시스템이 서로 영향을 주고 반복 가능한 재미를 만들면 더 좋은 게임이 될 수 있다.

개발 중에는 항상 다음 질문을 유지한다.

> 지금 만드는 기능이 이 게임의 핵심 재미를 실제로 강화하는가?

---

# 2. 먼저 게임의 정체성과 핵심 기둥을 확인한다

대형 작업을 시작하기 전에 프로젝트의 정체성을 짧게 설명할 수 있어야 한다.

가능하면 핵심 재미를 2~4개의 큰 축으로 표현한다.

예:

```text
탐험 + 전투 + 성장 + 정착
```

또는:

```text
수집 + 조합 + 전술 전투
```

새 시스템이 이 기둥 어디에도 연결되지 않는다면 독립적인 잡기능일 가능성이 있다.

기획이 긴 프로젝트에서는 큰 작업 단위가 끝날 때 기획서를 다시 읽고 다음을 확인한다.

- 최초 목표와 현재 구현이 같은 방향인가?
- 핵심 재미보다 주변 기능이 더 커지고 있지는 않은가?
- 새 기능이 기존 시스템과 실제로 연결되어 있는가?
- 플레이가 더 재미있어진 것인가, 단순히 더 복잡해진 것인가?

---

# 3. 시스템은 루프로 연결한다

대형 모드의 규모는 메뉴 수나 재화 수로 만들지 않는다.

좋은 시스템은 다른 시스템의 입력 또는 출력이 된다.

예:

```text
전투
→ 자원 획득
→ 장비/캐릭터 성장
→ 새로운 지역 접근
→ 더 위험한 적
→ 새로운 전투 선택지
→ 전투
```

```text
탐험
→ 발견/자원
→ 마을 성장
→ 생산력/편의 증가
→ 더 먼 원정
→ 새로운 위험
→ 방어/전투
→ 탐험
```

새 기능을 추가하기 전에 최소한 다음을 답한다.

1. 플레이어가 왜 이 기능을 사용하는가?
2. 무엇을 소비하는가?
3. 무엇을 얻는가?
4. 얻은 결과가 다른 어떤 시스템에 영향을 주는가?
5. 반복했을 때 새로운 선택이 생기는가?

5번까지 답할 수 없다면 단순 반복 작업일 가능성이 높다.

---

# 4. 콘텐츠 양보다 콘텐츠 밀도

아이템 100개가 아이템 10개보다 반드시 좋은 것은 아니다.

좋은 콘텐츠는 다음 중 하나 이상을 만든다.

- 새로운 플레이 방식
- 새로운 선택
- 새로운 위험과 보상 관계
- 기존 시스템과의 새로운 조합
- 다른 콘텐츠의 가치 변화
- 기억할 만한 장면

기존 검의 공격력만 조금씩 높인 변형을 대량 추가하는 것은 콘텐츠 양은 늘리지만 콘텐츠 밀도는 낮다.

대형 프로젝트에서는 **수평 확장**과 **수직 확장**을 구분한다.

### 수평 확장

완전히 새로운 시스템을 추가한다.

### 수직 확장

현재 핵심 시스템에 더 많은 상호작용과 선택을 추가한다.

새 메뉴를 계속 만드는 것보다 이미 중요한 전투, 성장, 탐험 등에 깊이를 추가하는 편이 더 가치 있는 경우가 많다.

---

# 5. 복잡함과 깊이를 구분한다

다음은 깊이가 아니라 관리 비용이 될 수 있다.

- 의미 없이 늘어난 재화
- 매번 해야 하는 반복 클릭
- 단순한 중간 제작 단계
- 서로 역할이 겹치는 여러 성장 시스템
- 설명만 길고 실제 선택은 없는 시스템
- 별도 메뉴를 하나 더 열어야 하는 기능

깊이는 적은 규칙에서 많은 의미 있는 결과가 나올 때 생긴다.

가능하면 새 규칙을 추가하기보다 기존 규칙끼리 상호작용하도록 만든다.

---

# 6. 성장에는 숫자 외의 변화가 있어야 한다

성장은 다음 종류를 구분한다.

### Numerical growth

공격력, 체력, 방어력 같은 수치 상승.

### Mechanical growth

새 스킬, 이동 방식, 상호작용 방식.

### Strategic growth

새 빌드, 역할, 조합, 장비 선택.

### Access growth

새 지역, 적, 자원, 콘텐츠 접근.

### Mastery growth

플레이어가 시스템을 배우며 실제 실력이 향상되는 성장.

큰 성장 시스템은 가능하면 수치 성장만 반복하지 않는다.

플레이어가 강해졌다는 느낌은 숫자가 커졌을 때뿐 아니라 **할 수 있는 일이 늘었을 때**도 생긴다.

---

# 7. 전투는 DPS만으로 평가하지 않는다

전투 감각은 다음이 함께 만든다.

- wind-up
- attack duration
- recovery
- movement restriction
- hit timing
- hit reaction
- knockback
- animation weight
- camera feedback
- VFX
- sound
- enemy response

따라서 사용자가 "공격이 느리다"고 했다고 공격 속도 변수만 바로 바꾸지 않는다.

가능한 원인은 애니메이션 시작 지연, 후딜, 이동 제한, 실제 판정 발생 시점, 피격 연출 타이밍 등일 수 있다.

"약하다"도 실제 DPS 문제일 수도 있지만 타격음, hit feedback, 적 반응, 화면 연출 때문에 그렇게 느껴질 수 있다.

**플레이어가 느낀 증상을 시스템 변수 하나와 바로 동일시하지 않는다.**

---

# 8. 보스는 큰 일반 몹이 아니다

보스는 높은 HP/공격력 외에 학습과 대응을 요구해야 한다.

기본적으로 다음 흐름을 고려한다.

```text
Telegraph
→ Player response window
→ Attack
→ Impact
→ Recovery / punish window
```

좋은 패턴은 다음을 갖는다.

- 읽을 수 있는 사전 신호
- 대응 방법
- 외형과 실제 판정의 정합성
- 성공했을 때의 명확한 보상
- 실패했을 때 이해 가능한 피드백
- 연속 공격 사이의 적절한 회복 구간

페이즈 변화가 있다면 단순 스탯 증가보다 플레이 방식 변화가 있는지 우선 검토한다.

---

# 9. 연출은 게임 정보이기도 하다

VFX와 애니메이션은 장식만이 아니다.

다음 정보를 전달한다.

- 공격 범위
- 위험 시점
- 방향
- 상태 변화
- 성공/실패
- 보상 가치

가능하면 다음 세 요소의 위치와 타이밍을 맞춘다.

```text
Telegraph
→ 실제 판정
→ Impact feedback
```

화려한 효과가 실제 판정과 다르면 플레이어는 불공정하다고 느낄 수 있다.

중요 전투 콘텐츠는 단순 vanilla entity + 기본 particle만으로 최종 처리하지 않는다. 프로젝트 중요도에 따라 모델, 애니메이션, 전용 텍스처, 사운드, 카메라 효과, 환경 반응 등을 검토한다.

---

# 10. 품질 예산은 플레이어 체감에 비례한다

모든 요소에 같은 시간을 쓸 필요는 없다.

플레이어가 자주 보거나 게임의 정체성을 대표하는 요소에 더 많은 제작 비용을 배분한다.

일반적인 우선순위 예:

```text
핵심 전투/핵심 루프
> 메인 UI
> 대표 캐릭터/보스/장비
> 반복 사용 시스템
> 주요 환경
> 일반 콘텐츠
> 드물게 보는 보조 화면
```

프로젝트에 따라 순서는 달라질 수 있다.

목표는 모든 요소를 동일하게 비싸게 만드는 것이 아니라 플레이어가 가장 많이 체감하는 부분에 품질을 집중하는 것이다.

---

# 11. 작업은 의미 있는 단위로 진행한다

서로 강하게 연결된 변경을 몇 줄씩 잘라 반복 커밋하고 매번 작업을 멈추지 않는다.

좋은 작업 단위 예:

- 전투 한 사이클 완성
- 캐릭터 한 계열의 핵심 플레이 완성
- 상점의 기능 + 상태 처리 + 기본 UX 완성
- 보스 한 페이즈 완성
- 하나의 UI 화면을 주요 상태까지 완성

반대로 버튼 하나, 텍스트 하나, 변수 하나처럼 독립적으로 의미가 거의 없는 수정마다 작업을 끊지 않는다.

단, 큰 작업 단위를 만든다는 이유로 서로 관련 없는 시스템을 동시에 변경하지 않는다.

---

# 12. 테스트 비용은 변경 위험에 비례한다

모든 변경마다 가장 비싼 검사를 반복하는 것도 좋은 품질 관리가 아니다.

### 문구/기획 문서

문서 정합성 검토 중심.

### UI 위치/비주얼

실제 화면 검수 중심. 관련 코드가 안전하다면 매번 full clean build를 반복할 필요는 없다.

### 순수 로직

관련 unit test와 코드 검토를 우선한다.

### 등록/API/네트워크/저장 구조

빌드, GameTest, 서버/클라이언트 경계와 회귀 검사를 강화한다.

### 테스트 JAR/릴리스 후보

`BUILD_STANDARD.md`의 전체 검증 계약을 적용한다.

검사의 목표는 적게 돌리는 것도 많이 돌리는 것도 아니다.

**변경의 실패 가능성과 실패했을 때의 비용에 맞는 검증을 선택한다.**

실행하지 않은 검사를 실행했다고 표시하지 않는다.

---

# 13. 사용자가 실제 Minecraft에서 검증해야 할 때

수동 플레이 검증이 필요한 작업은 "게임에서 확인해 달라"로 끝내지 않는다.

가능하면 다음을 함께 제공한다.

- 필요한 `/give`
- 필요한 `/summon`
- 필요한 `/effect`
- `/gamemode`
- `/tp`
- 테스트 전제 조건
- 재현 순서
- 정상이라면 보여야 할 결과
- 비정상일 때 관찰할 증상

테스트 전용 명령이나 아이템이 이미 프로젝트에 있다면 그것을 우선 사용한다.

사용자가 게임을 켠 뒤 테스트 방법을 다시 질문하지 않아도 되게 만든다.

---

# 14. 플레이테스트 피드백을 최우선 증거로 취급한다

실제 플레이에서 나온 다음과 같은 피드백을 단순 취향으로 무시하지 않는다.

- 너무 느리다
- 너무 오래 걸린다
- 약한 느낌이다
- 귀찮다
- UI가 못생겼다
- 정보가 안 보인다
- 연출이 밋밋하다
- 조작이 이상하다

이 피드백은 코드의 특정 줄을 직접 알려주는 것이 아니라 **플레이어가 관찰한 증상**이다.

작업자는 증상에서 가능한 원인을 분해하고 실제 구현과 비교한다.

수치상 정상이라는 이유로 플레이 감각 문제를 종료하지 않는다.

---

# 15. 플레이어에게 개발 과정을 노출하지 않는다

실제 게임의 플레이어-facing 텍스트에 다음과 같은 내부 표현을 넣지 않는다.

- P0/P1/P2
- alpha test system
- debug
- temporary
- TODO
- prototype
- developer
- 내부 작업 단계명
- AI가 만든 것처럼 보이는 설명

게임 안의 이름, 설명, 메시지는 세계관과 플레이어 관점에서 작성한다.

유명 작품에서 영감을 얻었더라도 독립 프로젝트의 명칭을 유명 IP 이름 그대로 붙이는 것을 기본 방식으로 삼지 않는다.

---

# 16. 프로토타입은 최종품이 아니다

가능성 검증을 위해 다음을 임시로 사용하는 것은 허용할 수 있다.

- 기본 particle
- placeholder texture
- vanilla button
- debug text
- hardcoded test value
- test item
- 임시 명령

하지만 기술 검증이 성공한 뒤 이를 정식 자산과 구조로 승격하지 않으면 프로토타입이 그대로 최종품이 된다.

중요 기능을 완료할 때 임시 구현이 남았는지 따로 확인한다.

---

# 17. 대형 프로젝트의 문서 역할을 분리한다

권장 역할:

### `PROJECT.md`

환경, 버전, 의존성, 빌드/테스트 계약.

### 기획서

게임의 목적, 플레이 루프, 시스템, 콘텐츠 방향의 정본.

### 수치/시스템 위키

세부 규칙과 밸런스.

### `CHANGELOG`

실제 구현 변경 이력.

### `QUALITY_STANDARD.md`

공용 제작 품질과 기술 기준.

### 이 문서

게임 설계, 시스템 연결, 개발 운영, 플레이테스트 해석 기준.

### `THIRD_PARTY_ASSETS.md`

외부 자산 원천과 사용 조건.

문서는 실제 구현과 함께 갱신한다. 오래된 문서를 새 코드보다 우선해서는 안 되며, 반대로 구현 변경으로 기획이 달라졌다면 문서도 갱신해야 한다.

---

# 18. 반복해서 피해야 할 실패 패턴

## Feature-first

게임 품질보다 기능 존재 여부만 우선한다.

## Quantity inflation

아이템, 적, 재화 수만 늘린다.

## Menu inflation

시스템 깊이 대신 메뉴를 늘린다.

## Stat inflation

성장 대신 숫자만 크게 만든다.

## AI temporary UI

즉흥적인 반투명 패널과 카드 조합을 최종 UI로 사용한다.

## Particle dependency

모델/애니메이션/타격 연출을 모두 particle로 대신한다.

## Prototype permanence

임시 구현을 최종품으로 방치한다.

## Direction drift

장기 개발 중 최초 기획의 핵심 재미를 잃는다.

## Build-driven destruction

빌드를 통과시키기 위해 기능을 삭제하거나 무력화한다.

## Test theatre

실제로 하지 않은 검증을 성공했다고 기록한다.

# 19. 새 기능 전 품질 질문

중요한 기능을 추가하기 전에 가능한 범위에서 다음을 확인한다.

1. 이 기능이 핵심 재미를 강화하는가?
2. 기존 플레이 루프의 어디에 연결되는가?
3. 플레이어에게 의미 있는 선택을 주는가?
4. 단순 관리 노동만 늘리지는 않는가?
5. 기존 게임/모드에 이미 더 좋은 해결 사례가 있는가?
6. 그 사례가 좋은 이유를 이해했는가?
7. Minecraft의 자유로운 월드와 멀티플레이 가능성에 맞게 변환했는가?
8. 외형, 애니메이션, UI, 사운드 품질이 기능 중요도에 맞는가?
9. 최악 조건의 성능을 고려했는가?
10. 콘텐츠가 늘어나도 유지 가능한 구조인가?
11. 기획서와 충돌하지 않는가?
12. 이 기능이 정말 필요한가?

# 20. 완료 판정 확장

`QUALITY_STANDARD.md`의 Definition of Done에 더해 대형 콘텐츠는 가능한 범위에서 다음을 확인한다.

- 핵심 플레이 루프에 실제로 연결됨
- 플레이어가 사용하는 이유가 명확함
- 불필요한 관리 복잡성을 만들지 않음
- 중요한 행동에 충분한 피드백이 있음
- 연출과 실제 판정이 모순되지 않음
- 프로토타입/placeholder가 최종품으로 남지 않음
- 실제 플레이 피드백 또는 재현 가능한 수동 검수 경로가 있음
- 기획서/위키와 실제 구현이 일치함

**코드가 완성됐다는 것은 게임이 완성됐다는 뜻이 아니다.**
