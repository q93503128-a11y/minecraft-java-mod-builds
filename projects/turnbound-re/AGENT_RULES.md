# AGENT RULES — TURNBOUND: RE

이 문서는 과거 반복 실패를 막기 위한 프로젝트 로컬 강제 규칙이다. 공용 `docs/QUALITY_STANDARD.md`보다 느슨하게 해석할 수 없다.

## 1. 가장 중요한 시각 디자인 규칙
**코드부터 만들지 않는다.** 특히 UI를 'RPG처럼 보이게' 하려고 어두운 반투명 사각형, 금색 테두리, 임의 그라데이션, 임의 아이콘을 조립하는 방식은 금지한다.

최종 시각 작업은 아래 순서가 강제된다.
1. 실제 상용 게임/검증된 Minecraft 프로젝트/허용된 자산에서 레퍼런스를 조사한다.
2. 무엇이 좋은지 정보계층, 배치, 입력 흐름, 여백, 크기, 타이포, 상태 변화, 애니메이션으로 분해한다.
3. TURNBOUND: RE에 필요한 정보와 불필요한 정보를 결정한다.
4. 디자인 토큰/레이아웃 규칙/컴포넌트 규격을 만든다.
5. 목업을 만든다.
6. 목업이 레퍼런스의 장점을 실제로 재현하는지 검토한다.
7. Minecraft에 구현한다.
8. 실제 게임 스크린샷을 목업/레퍼런스와 나란히 비교한다.
9. 차이를 수정한다.
10. 통과 후에만 production-ready로 표시한다.

레퍼런스 조사 없이 4단계 이후로 진행하면 실패다.

## 2. 적용 대상
- 전투 HUD/턴 타임라인/스킬 선택/대상 선택
- 캐릭터/편성/성장/장비/상점/도감 UI
- 캐릭터 외형과 고유 스킬 연출
- 몬스터 변형 외형
- 월드, 마을, 던전, 전투장, 건축물
- 아이콘, 프레임, 폰트, 색, 배경, 버튼
- 컷신과 카메라 연출

## 3. 허용되는 임시 시각물
M0~M4에서 전투 로직을 검증하기 위한 최소 UI는 허용한다. 단:
- 파일/화면/문서에 `DEBUG_ONLY` 표기.
- 최소 정보만 표시.
- 예쁘게 만들려고 시간을 쓰지 않음.
- 최종 디자인의 선례로 사용하지 않음.
- M5에서 교체 가능한 컴포넌트 경계를 유지.

## 4. 외부 참고 규칙
- 게임 메커니즘은 원리를 분석해 재설계한다. 이름/수치/화면/콘텐츠를 통째로 복제하지 않는다.
- 오픈소스 코드는 라이선스와 버전을 확인한다.
- 코드가 필요한 경우 파일 단위 출처를 `THIRD_PARTY_ASSETS.md`에 기록한다.
- 단순 구조 참고와 실제 코드 사용을 구분한다.

## 5. 구현 규율
- 클라이언트는 의도를 보낼 뿐 전투 결과를 결정하지 않는다.
- 핵심 공식은 데이터/테스트와 함께 유지한다.
- 버그 재현이 가능하도록 battle seed, revision, event log를 남긴다.
- 전투 로직은 렌더/UI에서 분리한다.
- TODO를 숨겨 완료로 보고하지 않는다.
- 빌드 성공 ≠ 게임성 검증 성공 ≠ 시각 품질 통과.

## 6. 완료 전 자가검사
- 구 TURNBOUND 규칙을 무의식적으로 가져오지 않았는가?
- 문서의 수치/상태 전이가 코드와 일치하는가?
- 데이터 검증 실패가 명확한 오류를 내는가?
- UI/연출이라면 레퍼런스와 실화면 비교 자료가 있는가?
- 외부 자료의 출처/라이선스를 적었는가?
