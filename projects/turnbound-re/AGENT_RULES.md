# AGENT RULES — TURNBOUND: RE

이 문서는 과거 반복 실패를 막기 위한 프로젝트 로컬 강제 규칙이다. 공용 `docs/QUALITY_STANDARD.md`보다 느슨하게 해석할 수 없다.

## 1. 가장 중요한 시각 디자인 규칙
**코드부터 만들지 않는다.** 특히 UI를 'RPG처럼 보이게' 하려고 어두운 반투명 사각형, 금색 테두리, 임의 그라데이션, 임의 아이콘을 조립하는 방식은 금지한다.

최종 시각 작업은 아래 순서가 강제된다.
1. 실제 상용 게임/검증된 Minecraft 프로젝트/허용된 자산에서 레퍼런스와 직접 사용 가능한 production asset/base를 조사한다.
2. 라이선스와 실제 반입 가능 범위를 먼저 확인한다.
3. TURNBOUND: RE에 필요한 정보/행동/상태를 외부 디자인에 어떻게 연결할지 결정한다.
4. 직접 사용할 외부 asset/base 또는 이미 승인된 프로젝트 visual family를 고정한다.
5. 필요한 경우 외부 asset 자체의 허용 범위 안에서 Minecraft 규격/상태/애니메이션 연결만 조정한다.
6. Minecraft에 구현한다.
7. 실제 게임 스크린샷을 원본 외부 디자인/asset과 나란히 비교한다.
8. 차이를 수정한다.
9. 통과 후에만 production-ready로 표시한다.

레퍼런스 조사 없이 구현으로 진행하면 실패다. 더 중요하게, **레퍼런스를 본 뒤 AI가 새 외형/UI를 재디자인하거나 비슷하게 재구성하는 것도 production 작업에서는 실패**다.

## 2. 적용 대상
- 전투 HUD/턴 타임라인/스킬 선택/대상 선택
- 캐릭터/편성/성장/장비/상점/도감 UI
- 캐릭터 외형과 고유 스킬 연출
- 몬스터 변형 외형
- 월드, 마을, 던전, 전투장, 건축물
- 아이콘, 프레임, 폰트, 색, 배경, 버튼
- 컷신과 카메라 연출

## 3. 임시/자체 디자인 금지
현재 단계부터 플레이어가 보게 될 시각물에는 아래 규칙을 강제한다.

- AI가 임의로 만든 placeholder model/texture/UI/VFX를 production path에 넣지 않는다.
- '외부 레퍼런스 참고'만 하고 새 geometry/skin/layout을 손으로 재구성하지 않는다.
- reference-only 자산을 눈으로 보고 닮게 다시 만드는 방식도 허용된 외부 디자인 사용으로 취급하지 않는다.
- 외부 production asset/base를 직접 쓸 수 없으면 다른 허용 자산을 찾는다.
- 적절한 외부 자산을 확보하지 못했으면 해당 visual work는 **BLOCKED**로 남기고 임시 디자인으로 메우지 않는다.
- Minecraft/Mojang의 기존 runtime model/texture처럼 게임에 이미 존재하는 검증된 외부 디자인을 직접 사용하는 것은 허용한다.
- mockup이 필요하면 승인된 외부 sprite/model/UI family를 실제로 조합해서 만든다. 자체 임시 미술을 넣지 않는다.
- 순수 개발자용 진단 overlay는 플레이어-facing 화면과 완전히 분리되고 release path에서 비활성화되는 경우에만 예외다.

기존 구현 중 이 규칙 이전에 'reference → 수동 재구성'으로 만들어진 시각물은 자동으로 production-final로 인정하지 않는다. 외부 직접 사용 여부를 다시 감사하고 교체한다.

## 4. 외부 참고/자산 규칙
- 게임 메커니즘은 원리를 분석해 재설계한다. 이름/수치/화면/콘텐츠를 통째로 복제하지 않는다.
- 오픈소스/공개 자산은 라이선스와 버전을 확인한다.
- 실제 코드/모델/텍스처/UI/VFX/사운드를 사용하면 원본 URL, commit/tag 또는 배포 버전, 파일 경로, 라이선스, 수정 내용을 `THIRD_PARTY_ASSETS.md`에 기록한다.
- 단순 구조 참고와 실제 asset/base 직접 사용을 구분한다.
- proprietary/ARR/reference-only 자산은 허용 범위가 명확하지 않으면 파일을 반입하거나 수동 복제하지 않는다.

## 5. 구현 규율
- 클라이언트는 의도를 보낼 뿐 전투 결과를 결정하지 않는다.
- 핵심 공식은 데이터/테스트와 함께 유지한다.
- 버그 재현이 가능하도록 battle seed, revision, event log를 남긴다.
- 전투 로직은 렌더/UI에서 분리한다.
- TODO를 숨겨 완료로 보고하지 않는다.
- 빌드 성공 ≠ 게임성 검증 성공 ≠ 시각 품질 통과.

## 6. 완료 전 자가검사
- 구 TURNBOUND 규칙을 무의식적으로 가져오지 않았는가?
- 문서의 수치/상태 전이가 코드와 일치하는가?
- 데이터 검증 실패가 명확한 오류를 내는가?
- UI/연출/외형이라면 실제 외부 디자인/asset/base를 직접 사용했는가?
- reference-only 자료를 눈으로 보고 새 디자인을 만들어 넣은 것은 아닌가?
- 실제 게임 화면과 외부 원본을 비교할 수 있는가?
- 외부 자료의 출처/라이선스/반입 상태를 적었는가?
