# 군체술사 — 0.2블록 소형 개체 및 서버 군집/AI·투사체·비행 기술 타당성 검토

> 2026-11-05 / **DESIGN REVIEW / TECHNICAL RISK ASSESSMENT ONLY.** 아직 프로젝트 버전·loader 미정. **코드/빌드/JAR/실제 Minecraft 실행/멀티플레이/성능 프로파일링은 하지 않았음.** 이번 사용자 최신 결정은 **군체 개체 본체 길이 약 0.2블록**을 목표로 하며, 후반의 많아지는 군체를 **물리 개체 한 마리당 독립 AI로 전부 표현할 필요 없음**. ## 1. 0.2블록 크기가 적합한 이유와 위험

- **유지할 최신 사용자 목표: 개체 본체 길이 약 0.2블록.** 기존 문서에 남은 0.25~0.35블록은 초기 미술 시안이며 최신 0.2블록을 우선. 키/몸통 높이, 턱과 다리의 상대 비율, 펼친 날개 폭은 **실제 화면 검토 후 결정**.
- **이점(설계 판단):** 군단이 커져도 개체 하나가 시야/활 조준점·블록 설치를 차지하는 면적이 작고, 같은 공간에서 빽빽한 군집이 형성돼 후반 체급을 보이기 좋다.
- **위험 1(시각):** 실제 픽셀/화면 크기는 카메라 거리·FOV·해상도에 따라 급격히 작아진다. 0.2블록 개체는 4~8블록 거리에서 아주 얇은 다리/입 부분이 사라질 수 있으므로 **갑피·머리·턱·펴진 날개 등 큰 실루엣만 중요도가 높다.** 가까운 한 마리와 군집 전체의 판독성을 각각 검수할 것.
- **위험 2(타격):** 모든 개체의 물리 hitbox가 0.2블록이면 화살이나 근접 몹의 AI와 효과적인 엄호를 연결하기 어려울 수 있다. 개체의 **렌더 모델 외형 길이**와 서버의 **군집 유효 충돌 체적**은 다른 설계 변수지만, 눈에 없는 큰 보호벽이나 실제 모델 밖으로 무한 확대된 hitbox는 금지.
- **위험 3(성능):** 클라이언트도 개체별 복잡한 bone/날개 물리·소리·그림자를 100개 이상 모두 동시에 갱신하면 비용이 커진다. **서버 논리 N=128이라도 실제 보이는 리그 인스턴스 수/LOD는 성능 실측으로 정할 것**. 게임 내 최종 효과가 단순 파티클 구름만 남으면 시각 목표 실패.

## 2. 핵심 구조 가설: 한 플레이어의 실제 군체 수량을 서버가 소유

`totalAlive=attackN+guardN+liftN+regroupN`, 모든 항목 정수·0 이상·총수는 레벨에 따른 `Nmax` 이하. 실제 보이는 개체 sample 수는 이 식의 항목으로 합산하지 않으며, 렌더 계산 때문에 서버의 개체 수가 줄거나 늘지 않는다.

**서버 후보 데이터:**
`ownerUUID, N, Nmax, attackN, guardN, liftN, regroupN, selectedTacticId, priorityTargetUUID, groupCenters, targetCenters, movementStates, pendingDamageByRole, flightState`와 실제 필요한 저장/동기화 범위. 플레이어 직접 정의 전술의 공격:엄호 비율·이름은 별도 서버 저장.

**시각 후보 구조:** 한 종의 0.2블록 소형 생물 모델을 여러 개 재사용하고 소수 군집 중심 및 결정적 피해 이벤트를 기반으로 주변 모션/밀집도/날갯짓 위상을 클라이언트에서 계산. 어떤 군집은 실제 유효 충돌 proxy를 제공하지만 수십 마리마다 별도 서버 Pathfinding Mob/UUID를 만들 필요는 없게 한다.

**필수 분리:** `실제 논리 개체 수` / `서버 엄호·공격 충돌 체적 수` / `클라이언트 렌더링 생물 인스턴스 수` / `한 프레임의 애니메이션 평가 수`는 다른 값이다. 이 차이를 플레이어가 믿을 수 있게 **사망 연출·군집 크기·HUD 숫자/피해·투사체 방어 위치**로 연결해야 한다.

## 3. 구현 차단 위험과 우선 기술 검증

| 우선 | 기술 위험 | 아직 검증되지 않은 이유 | 최소 검증 결과(성공 시에만 통과) |
|---|---|---|---|
| **G1: 차단** | **바닐라 적 AI가 군체를 때릴 수 있는가** | 단순 충돌 proxy/일반 Entity만 월드에 둔다고 좀비·스켈레톤이 자동 공격 대상으로 삼지 않음. 바닐라 몬스터별 target goal/피해 방식이 다름 | 실제 좀비가 군체를 적법한 대상으로 인지해 접근·근접 타격→서버 군체 N 감소→장면 반영. 성공하지 않으면 표적 어댑터/군체 형태 재설계 |
| **G2: 차단** | **실제 적 화살을 엄호군이 가로막는가** | 투사체의 이동·raycast/충돌·발사자 관계와 군집 hitbox가 맞아야 함. 모델만 렌더했다고 탄체에 맞지 않음 | 스켈레톤 화살이 **보이는 엄호 위치**와 실제 교차할 때, 정확히 1회 군체 피격/소실·플레이어 동일 피격 방지. 빗나간 화살/엄호0%는 정상 플레이어 피해 |
| **G3: 차단** | **서버 총 N 보존·작은 군집 실제 피격/소모** | 원격 목표 변경·피격·소모·자동 재증식·재분할이 같은 서버 갱신에서 일어날 수 있음 | 상태 변경마다 `attack+guard+lift+regroup=N`, N>=0, N<=Nmax; 동일 화살/소모 비용 중복 감산·개체 복제 없음 |
| **G4: 높음** | **비행대 실제 운반과 안전 하강** | 이동 권위·서버 위치 보정·충돌·물/벽/엘리트라/승차 등 충돌점이 많고, 비행 중 군체 죽음이 수량 손실과 이어짐 | 공중 정지·상승·하강 성공, 비행대 피해/부족 시 유효 재배치 또는 **즉시 추락사가 아닌 감속 하강**, 공중 무적/무한 비행 악용 없음 |
| **G5: 높음** | **0.2블록 모델 가독성과 대군단 렌더 부담** | 근접 모델 조명/텍스처/LOD·카메라·셰이더·멀티 실측이 없음 | N16/48/80/128에서 개체 실루엣과 군집 밀도·피격/증식 구분, 1·3인칭 조준 방해 없음. 동일 조건 FPS/메모리/렌더시간 측정 |
| **G6: 높음** | **외부 몹/투사체·PvP·멀티 호환** | 바닐라의 AI·DamageSource/피해 판정과 외부 모드의 커스텀 공격 방식이 일치하지 않음 | 호환 목록을 실제 시험된 적/투사체로 제한·표기, 아군 공격 제외, 자기 화살 엄호 방해 없음, 2~20인 다수 군체 TPS/패킷 테스트 |
| **G7: 품질** | **전술 UI/저장과 실제 군집 재배치** | 커스텀 이름/비율 즉시 반영과 멀리 있던 공격대의 실제 귀환 사이에 시간차 | 사용자 직접 만든 전술의 0:100/100:0/중간 비율 유지, 퀵 편집/저장/재접속, 즉시 목표/시간 걸리는 실제 재배치가 정확히 구별 |

**가장 먼저 해결할 G1·G2가 실패하면** 화려한 외형/비행을 먼저 완성해도 적이 실제로 죽일 수 있는 군체라는 정체성을 충족하지 못한다. **타 직업 로더를 복사해 채택하거나**, 시작부터 모델·GUI 10개/군체 전투 100종을 동시에 만들지 않는다.

## 4. G1·G2를 시험할 때의 구체적 실험 시나리오

### 바닐라 몹

1. **지상, 사용자 지정 엄호100%·공격0%**: 정상 좀비가 플레이어에게만 달려드는지 군체도 공격 대상으로 삼을 수 있는지 관찰. 실제 군체 proxy의 공격 타깃 지정/캠프 반경·적 AI 변경의 부작용을 측정. 단순 '좀비가 플레이어 공격→군체 N을 임의로 대신 감소'는 **실제로 군체를 때린 것과 다른 가짜 방식**이므로 목표 충족 실패.
2. **지상, 사용자 지정 엄호100%**: 정상 스켈레톤 화살을 정면/측면/상하 각도 3개 이상에서 시험. 엄호군의 실제 위치에서만 충돌, 유효 엄호 내구/개체수 손실·플레이어 보호 여부 일치. **화살이 보이는 무리를 통과하는지, 보이지 않는 무리에 맞는지** 각각 확인.
3. **지상, 사용자 지정 공격100%**: 엄호군 없음. 스켈레톤 화살이 공격대와 우연히 충돌한 경우 그 개체는 맞을 수 있지만, **플레이어 주위에 무료 보호 기능이 생기면 실패**. 공격대 원격 표적·군집 급습·군체 소모가 엄호군/비행군을 몰래 동원하지 않는지 확인.
4. **지상 사용자 정의 공격50%·엄호50%**: 서로 다른 군집 센터에서 목표를 공격하고 보호, 실제 피격·소모·자연 재증식이 전체 N 보존.
5. **비행 중**: 플레이어 위치가 바뀌면서 적 화살/광역 피해가 실제 엄호군/비행군에 적중하면 그룹별 수량 감소, 비행대 부족 시 유효 재배치 또는 안정 하강. 총 N이 갑자기 +30으로 되지 않음.

### 순서/상태 회귀

- 전술 퀵 전환 직전 날아온 화살이 군체가 아직 도착하지 않은 위치에서 자동 차단되면 **실패**.
- 공격군을 희생한 `군체 소모`와 적 화살 피격이 같은 tick에 발생할 때 `N` 이중 감산/소실 중복 처리 금지.
- N=0 → 자연 증식, 스탯/매개체 교체, 사망/재접속·차원 전환·청크 언로드, 서버 종료/재시작 뒤 소유자 유령 군집/복제 없음.
- 아군의 화살/쇠뇌·소환물/인형/정신지배 대상과 서버 소유권 관계의 다른 부작용 검수.
- 원격 표적이 로드되지 않은 다른 차원/벽 뒤에 있어도 서버가 억지로 즉시 피해를 주면 실패.

## 5. 실제 Minecraft 구현 시작 순서 (구현 착수 아님)

**M0: 환경 선택·기술 검증 준비**
- Minecraft 버전·loader는 이 프로젝트에서 아직 미정. Fabric/NeoForge 후보별 **목표 버전의 실제 엔티티·투사체/AI/네트워킹/렌더/GeckoLib 버전** 및 다른 선택 외부 몬스터/전투 모드 호환을 확인한 후 결정. 한 번 선택해 승인된 기술 스택/버전은 문서로 기록.
- `AGENTS.md`, `docs/BUILD_STANDARD.md`, `docs/QUALITY_STANDARD.md`, 공용 dev-playbook 최신 정본 준수.
- 아직 프로젝트 코드가 없는 경우 **첫 목표는 게임 전체 개발이 아닌 G1/G2 핵심 기술 실험**. 실험용 나쁜 임시 UI·개발자 메시지를 실제 플레이어용 콘텐츠에 남기지 않는다.

**M1: 단일 군집 서버 전투 검증**
- 서버 군체 논리 N/근처의 단일 실질 피격 가능한 군집 객체와 엄호 대상 위치 구성.
- 유효 피해·타격 후 N 감소 및 N=0/중복 hit 처리, 소유자/팀 필터. 실제 좀비의 AI 타깃 획득/근접 공격을 검증. AI가 군집을 공격하지 않으면 다른 방식/어댑터 적용안을 실험해 구조를 바꾼다.

**M2: 투사체 가로막기 핵심 검증**
- 바닐라 **화살부터** 정상 projectile collision과 실제 엄호 개체 소실/상호 위치를 검증. 소유자/아군 화살 통과, 엄호0에서 보호 안 됨. 화염구·빔/커스텀 외부 투사체는 다음 범위로 밀어둔다.

**M3: 한 종의 실제 0.2블록 생물 모델·최소 모션**
- 먼저 **Blockbench에서 본체 길이 약 0.20블록 베이스** 제작/실제 Minecraft 내 조명·카메라·타격 위치 검수. 공격/엄호/피격·사망/재증식 최소 모션만 정교하게. 모델 외부 라이선스 확인 전 사용 금지.
- 가까운 군집의 생물은 알아볼 수 있게, 멀리 갈수록 렌더 샘플·애니메이션 계산·날개 가독도 LOD 검토. 화려한 모델을 먼저 대량 생산하지 않는다.

**M4: 사용자 전술·원격 표적·실제 집단 이동**
- 직접 이름/공격%를 저장해 퀵휠 변경하고 목표 역할/실제 위치·재결집 차이를 정확히 반영. `군집 엄호` 별도 액티브 없음. 급습/소모 두 공격 액티브의 시각 예고·서버 타격/개체 소모를 연결.

**M5: 군체 운반 비행**
- 운반군 예약/호버 이동/실제 피격 감소→안전 하강. 비행에 필요한 마릿수·속도·비행 해금 레벨은 실제 이동/전투 상호작용 실측 후 조정.

**M6: 콘텐츠·품질 확장**
- 장비·스킬 트리 수치/피해·내구·재증식 밸런스 조정, 모델 세부 애니메이션·비행/사운드, 실제 화면 UI 검수, 외부 몬스터·멀티 성능. 중력술사·공명술사 상세는 사용자 지시 전 보류 유지.

**검증 횟수는 위험에 비례.** 기술 게이트를 구현해 실제 서버를 실행할 때는 관련 좁은 테스트와 필요한 build, 통합 체크포인트에서만 CI. 모델/텍스처·문구 수정을 할 때마다 의미 없이 clean build 반복 금지.

## 6. 리스크를 줄이면서 재미를 보존할 설계 선택

- **작은 생물이 실제로 맞아 죽는 재미 > 충돌체를 매우 복잡하게 분할하는 복잡성.** 0.2블록 한 마리마다 Entity 1개라는 정의는 하지 않고, 군집 중심 1~소수 충돌 영역과 그 안의 시각 생물 밀집도를 납득 가능하게 만든다.
- **플레이어에게 4개 모드 제공 금지.** 사용자 전술 이름/공격:엄호 비율만 사용, 관리/빠른 편집 가능. 비행에 필요한 수량만 먼저 예약. 엄호 액티브·수량 즉시 증가 버튼·전용 연료/포만감 게이지는 제외.
- **사전 전술 없이 처음 접속해도 기본 동행/생존은 가능**해야 하나, 고정 이름 전술을 자동 생성하지 않는다. 전술 직접 편집을 시작하는 흐름은 짧게 만들 것.
- **극소형 개체의 실루엣/가독도와 체급 상승은 별개.** 늘어난 군체의 시각 밀도/분할 공간/이동·공격 임팩트가 커져야 하며 모델만 크게 바꾸거나 검은 연기·카드 UI 추가로 대체하지 않는다.
- **군단 유효 hitbox를 크게 할수록 방어력이 일방적으로 커지는 문제**와 **군체 0.2블록이라 화살을 전혀 못 막는 문제** 사이에 밸런스가 필요하다. 적의 1회 화살 보호 성공에 필요한 군체 손실/밀도/운반군 방어 관계를 측정 후 조정. 보호 성공률을 시야나 유효 전술 비율과 무관한 상수로 처리하지 않는다.
- 무제한 레벨은 N만 무제한 서버 엔티티로 늘리는 것이 아니라 **Nmax와 함께 개체 기본 공격력/내구·증식 품질이 성장**. 기존 Lv1/25/100/500 N16/48/80/128, DPS/내구는 모두 **유저 미승인/미검증 벤치마크 후보**로 보존.

## 7. 성능·체감 검수 행렬

| 검증군 | 실측 변수 | 결과로 남길 것 |
|---|---|---|
| 생물 본체 길이 약0.2블록 | 1인칭/3인칭·FOV/해상도·동굴/야외/수중/비행 | 근접 생물 형태·먼 군단 실루엣/가려진 시야·hitbox와 보이는 개체 불일치 |
| N16 / 48 / 80 / 128 | 공격·엄호·비행/시각 개체 렌더 수와 골격·LOD | 1명 기준 client FPS, frame time, render draw calls 추정/측정, 서버 mspt, 메모리 |
| 플레이어 동시 군체 1 / 2 / 8 / 20명 | 중립/원격 표적/보스 전투·동시 스킬/화살 피격 | 서버 tick(mspt), 네트워크 전송량, 월드 엔티티 수, 클라이언트 FPS, 소유자 UUID 섞임 |
| 어택·보호 | 좀비 근접, 스켈레톤 화살, 아군 활, 보스 근접·폭발 | 유효/무효 타격 횟수, 플레이어/군체 피해 이벤트의 중복, 수량 변화, 텔레그래프-타격 판정 일치 |
| 비행 | 저수량과 정상수, 화살 지속 피해, 포탈/재접속/청크 언로드 | 초당 이동/상승/착륙 속도, 조종감, 서버 위치 보정, 추락·무적 악용 |

**측정 제안:** 대조군은 군체 없는 같은 월드/같은 몬스터/같은 화면·하드웨어. 정상 20 TPS 지향(서버 한 tick 처리에 대략 50 ms 예산)은 참고 목표일 뿐, **빌드·성능 실측한 결과가 아니다**. 불안정하거나 공존 모드 수가 늘어나는 조건에 대한 실제 목표 수치는 테스트 환경이 정해진 뒤 문서화.

## 8. 외부 자료 — 사실과 프로젝트 판단을 구분

1. [Fabric 공식 Creating Your First Entity](https://docs.fabricmc.net/develop/entities/first-entity): 몹 구현 시 `Mob`/`PathfinderMob`와 goal/렌더 구조를 구분한다. **AI가 어떤 Entity든 자동으로 타격한다고 주장할 근거는 없다**. Fabric은 **현재 검토용 예시이지 이 프로젝트에 선택된 로더가 아님**.
2. [Fabric 공식 Custom Projectiles](https://docs.fabricmc.net/develop/entities/projectiles): 투사체를 별도 Entity·충돌/기능으로 구현하는 API의 대표 예시. 투사체마다 충돌 방식이 같다고 일반화하지 않음.
3. [Minecraft Wiki Projectile Collision](https://minecraft.wiki/w/Projectile#Collision): projectile 이동 경로의 블록/엔티티 교차 검사 및 타입별 다른 충돌 처리를 설명. **독립 모델 크기=피격 확률/실제 방어 성공률을 바로 결정하지 않는다**.
4. [GeckoLib 공식 Blockbench 연계](https://wiki.geckolib.com/docs/geckolib5/making-models/blockbench-plugin-usage/) 및 [Blockbench 모델 형식](https://blockbench.net/wiki/blockbench/formats/): 모델·리그·애니메이션 제작 가능성 참고. **다수 인스턴스의 CPU/GPU/LOD 성능을 이미 검증한 자료는 아니므로 측정 필요**.
5. [GeckoLib Modrinth](https://modrinth.com/mod/Geckolib): Fabric/NeoForge 지원·현행 호환 버전은 적용 시 재확인. 라이브러리 선택과 프로젝트 loader 확정은 별개.
6. 기존 [AGENTS](../../../AGENTS.md), [품질](../../../docs/QUALITY_STANDARD.md), [빌드](../../../docs/BUILD_STANDARD.md) 계약과 문승준 공용 dev-playbook 최신 main을 동등한 작업 컨텍스트에서 준수.
