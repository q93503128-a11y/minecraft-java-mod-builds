## 결론: 직업 콘셉트는 많이 설계했지만 게임 전체 기획은 아직 완료되지 않음

- **1~6직업의 핵심 재미/주요 기능/성장 방향 문서가 있음**: 정신 지배자, 인형술사, 기생술사, 결계술사, 계약술사, 군체술사. 이 사실은 여섯 직업이 모두 최종 확정/기술 검증/실플레이 완료됐다는 뜻이 아니다.
- **7~8직업은 보류**: 중력술사·공명술사. 기존 예정 직업 목록을 보존. **출시 시점에 6개만 사용할지 / 향후 포함할지 역시 별도 결정 대상**이지 자동으로 폐기되는 것은 아님.
- **공통 RPG 루프는 큰 방향만 정리**되어 있다: 바닐라 생존 + 공통 경험치→레벨→스킬 포인트→직업 성장, 레벨 상한 없음, 공통 직업 매개체 슬롯 1개와 5등급 이름. 그러나 XP 지급·레벨 곡선·직업별 자동 성장/수치 합성·아이템/전리품 경제/탐험 보상/사망·재접속/직업 변경 등의 일관된 **플레이 가능한 세부 계약**은 아직 불완전하거나 미결정.
- **UI/모델/애니메이션/VFX/사운드**는 방향·정적 시안/설계 자료는 있으나 **최종 플레이어용 자산/실제 게임 화면 미제작**.
- **Minecraft 버전·loader·dependency·보스/외부 몬스터 모드 미선정**. 기획만 보고 구현 가능한 것처럼 주장할 수 없고, 렌더/AI/투사체/변신 등은 위험도 검증이 필요.
- **코드·빌드·JAR·Minecraft 플레이테스트·멀티플레이 테스트 없음**. 지금 바로 대규모 구현/첫 군체부터 완성 코딩을 시작할 단계가 아니라 **정본 정리·공통 게임 루프와 직업 간 비교→최소 기술 실험→구현 범위 확정** 순서가 적절.

## 2. 공통 결정이 끝나야 각 직업 수치도 의미가 생기는 부분

1. **직업 공통 기본값/수치 체계**: 공통 기초 HP/공격/방어/이동/XP/스킬포인트 지급·소모, 무제한 레벨 성장 곡선, 랭크 상한 이후 포인트 처리, 레벨별 자동 성장·PvP/외부 모드 적 레벨 보정, 무한 성장과 서버 수치 폭주의 수학적 제어. 사용자 선택/기획 명시가 없는 기본값 자동 삽입 금지.
2. **핵심 서바이벌 플레이 동선**: 원래 Minecraft의 채굴·건축·제작·탐험·전투와 클래스 능력이 어떤 보상/선택으로 연결되는가? 적을 때리면 무조건 XP만 주는 빈약한 RPG 루프/별도 재화와 하위 UI 무분별 증식 모두 지양. 바닐라 적, 외부 몬스터/보스, 드롭/재료, 매개체 5등급 재료 획득, 탐험 목표·난이도 곡선 연결.
3. **월드 및 콘텐츠 범위**: 제단/인형제작대/클래스 장비 제작·외부 보스의 스폰·충돌·보상/원거리 탐험·멀티 협동 목표, 네더·엔드 이동 여부 등 **요구하지 않은 조건 임의 추가 금지**. 어떤 구조가 게임의 목표인지 공통 장표로 명료화.
4. **직업 공정성**: 강점·약점·입문 편의/약한 상태의 회복·성장 속도·전투 성능/서바이벌 유틸리티/보스와 몬스터 호환성의 **실효 비교**, 단일 수치 DPS와 플레이 느끼는 강함 분리. 다른 종류의 소환물/제물/숙주/결계/군체가 전부 같은 방식의 노동·성능이 되지 않게 함.
5. **멀티/저장/보안 계약**: 소유자/파티/팀 피해, 사망·부활/언로드/재접속/차원 이동, 직업 변경/선택 잠금 또는 초기화, 데이터 저장·월드 호환, 외부 모드로 인한 예상치 못한 악용. `ALLY_RELATIONS.md` 같은 공통 계약 재사용.
6. **UI/UX/자산 완성 기준**: 6직업의 실제 단축키/직업 매개체 슬롯/전용 관리 패널·HUD와 양손 사용, 외부 게임 레퍼런스·디자인 자산/라이선스·인게임 1/3인칭 가독성/액티브 시각과 타격 동기화. 정신 지배자용 HTML 정적 예시를 전체 6직업 최종 UI로 혼동하지 않는다.
7. **기술 환경/외부 자산 선택**: Minecraft 버전과 Fabric/NeoForge 후보를 **클래스 실체 제어/엔티티/애니메이션/투사체/이동/서버 멀티** 요구에 맞춰 비교. 실제 관련 외부 몬스터·전투·보스 모드/GeckoLib/라이선스·업데이트/호환 확인. 다른 모드 개발 프로젝트의 loader 강제 상속 금지.

## 3. 지금 가장 중요한 문서 정리 문제

- `PROJECT.md`의 **'다음 기획 과제: 정신 지배자부터 순차적 상세 스킬'**, `GAME_DESIGN.md`의 **'8직업 기획 후 UI 구현'** 등 일부 표현은 이후 진행한 6직업 상세 설계/2직업 보류와 **현재의 다음 작업 순서가 다름**. 과거 본문을 아카이브로 보존하되 **하나의 최신 상태 요약**으로 최신 결정·보류·미결을 명확히 연결할 것.
- 군체술사 `SWARM_CASTER.md` 맨 앞 **1차 미승인 액티브 후보 `급속 증식`**, 3~4차 **`군집 엄호` 액티브 후보**, 기존 고정 **'자동/공격 우선/균형/엄호 우선' 전술** 등 **사용자가 이후 폐기한 안**이 기록상 남아 있음. 최신 승인 정본에는 **현재 두 공격 액티브 급습/소모 + 상시 엄호 전술 + 사용자가 직접 이름/비율 지정 + 자동 증식 + 원격 표적/비행**만 현행 규칙으로 승격해야 한다.
- **군체 0.2블록**이 모델 본체 크기 최신 방향이다. 군집 실제 충돌체/투사체 피격까지 개체마다 정확히 0.2블록 서버 LivingEntity를 강제하는 것은 별개의 기술적 가정이며 아직 시험하지 않았다.
- 각 직업 문서에 서로 다른 수치(270/285/290/300랭크, 공격력 계수, HP/유지비/쿨타임)가 **아직 비교·동일한 상대 스케일에서 검증되지 않음**. '사용자 승인 규칙' vs '제작자 검증안' vs '폐기/보류안'을 문서와 데이터에서 구별한다.
- **계약술사**는 16존재/제단 상세 기획이 있지만 `PACT_CASTER.md` 상단과 일부 옛 문단에 '다음 채팅에서 상세설계' 같은 시차 표현이 존재. 실제 문서 연결/우선순위 재정리 필요.
- 지금까지 기획서 수량이 많다는 사실은 **기획 완료 증거가 아니다**. 사용자가 게임을 켜서 무엇을 하게 될지, 진행이 막히는 상황/귀찮은 노동/반복·무한 성장 루프가 매끄러운지가 아직 최종 평가 대상.

## 4. 권장 순서: 4단계 정리 후 최소 구현 실험

**A. 최신 정본 통합(문서 작업만, 필수)**
- `PROJECT.md`/ `GAME_DESIGN.md`를 **현재 확정·현재 후보·폐기·보류·검증 상태**로 한눈에 볼 수 있게 정리. 이전 세부 기획을 삭제하거나 정리 이유 없이 축소하지 않는다.
- 각 1~6직업의 **핵심 판타지, 기본 능력, 액티브/패시브, 성장/아이템/드롭, 관리 키/HUD, 생존 일반 행동, 사망/멀티, 미결 수치**를 공통 형식으로 뽑은 직업 요약표를 만든다. 문서간 충돌 시 사용자 최신 승인을 우선한다. 7·8은 '보류'로만 보존.

**B. 공통 서바이벌/성장 플레이 연결(기획, 필수)**
- XP/레벨/스킬포인트/자동 능력치/매개체 단계/바닐라 채굴·탐험·전투·보스/재료 경제와 협동의 **한 가지 중심 플레이 흐름**을 먼저 정의.
- 예) 초반 오버월드 생존(실제 유효 직업 시작 능력) → 전투/채굴·장비 제작 → 매개체 등급과 스킬 성장 → 탐험과 강적 전투 → 상위 장비/성장 선택 → 장기·무제한 레벨. **예시일 뿐 새 고정 스테이지/신규 재화/퀘스트 시스템을 임의로 확정하지 않는다.**

**C. 6직업 동일 기준의 '기획상 플레이 동선 검토'(필수, 실제 플레이테스트 아님)**
- 1레벨·초반·중반·보스·장기 성장 5장면에서 **직업을 선택한 사람이 직접 무엇을 조작/소모/얻는지**, 전력 체감·재료 접근/문턱/이동/시야/단축키/직업 취약 순간·멀티 동작을 각각 비교.
- 전투시간과 생존 편의가 지나치게 불리하거나 시각 효과와 피해/진형이 어긋나는 직업부터 수정. 각 직업의 스킬 랭크 총합이 같아야 한다는 숫자 맞추기보다 **실제 직업 강점의 선택과 재미**를 우선.
- 이때 전체 8개 직업을 강제로 완성/재기획하지 않는다. **현 6개에만 적용**, 2개 보류 유지.

**D. 제작 가능성 게이트/기술 스택 선정(설계·검증 계획, 필수)**
- 버전/loader/외부 몬스터/라이브러리의 검증된 후보 목록, 각 직업의 실현이 특히 어려운 능력(지배/AI 인형/숙주 제어/결계/제단·권능/군체 hitbox+비행)을 테스트 매트릭스로 작성.
- **G1 몹의 군체 실제 공격, G2 화살 군체 직접 충돌** 같은 작고 위험한 기술 실험은 **위 A~C의 핵심 설계 정리 뒤** 시작할 수 있다. 하지만 **그때도 전체 군체를 먼저 완성하지 않으며**, 실험 결과가 나쁘면 공통 기술 구조를 다시 조정한다.
- 기술 실험 성공 후에야 **게임 공통 기반→직업별 기능 단위 구현→실제 인게임 모델·UI/사운드/성능 QA**를 이어간다. 테스트 JAR/CI는 기술 위험/마일스톤에 비례해 사용.

## 5. 구현 착수 여부를 결정할 단일 체크리스트

- [ ] 1~6직업의 **최신 승인 규칙/미확정 수치/폐기안**이 혼동 없이 하나의 기준으로 요약돼 있다.
- [ ] 7~8직업의 **보류**가 출시 범위 결정과 혼동되지 않고 명확하다.
- [ ] 공통 **경험치·레벨·스킬 포인트·능력치·아이템/드롭/탐험·제작 루프**가 직업 6개에 일관되게 적용된다.
- [ ] 1~6직업을 **같은 조건으로 초기 생존~상위 성장까지 문서상 검토**했다.
- [ ] 사용자 조작/UI/HUD/모드 간 주요 키 충돌, 사망·저장·PvP·멀티 역할이 명세돼 있다.
- [ ] 목표 Minecraft 버전·loader/외부 의존성과 기술 위험 순서가 정리돼 있다.
- [ ] AI/투사체/비행/숙주 등 위험 기술의 **최소 실험 계획/성공·실패 기준**이 문서화됐다.
- [ ] 실제 실험 결과가 없는 항목을 **BUILD VERIFIED / PLAYTESTED / MULTIPLAYER TESTED**로 잘못 표시하지 않는다.

**현재 판정: 위 항목 다수가 미완료이므로 '전체 구현 착수'는 아직 NO. 기획 정본 통합부터 진행하는 것이 다음 작업이다.** 단 최종 수치 전부가 완벽하게 정해지기 전에도 작고 고위험 기술 실험은 가능한 시점에 허용한다(실험과 게임 전체 구현을 구분).
