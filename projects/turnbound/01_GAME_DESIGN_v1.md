# TURNBOUND Game Design v1

> 역할: TURNBOUND 대격변 이후의 게임 방향/플레이 경험 정본.
> 수치 공식은 `02_BALANCE_RULES_v1.md`, 캐릭터별 전투 설계는 `03_CHARACTER_DESIGN_v1.md`를 따른다.
> 이전 Aster March 좌표/챕터/제작 셀은 정본이 아니다.

## 1. 한 줄 정의

TURNBOUND는 **Minecraft Java의 거대한 3D 판타지 월드를 직접 여행하면서 동료를 모으고 성장시키고, 필드에서 만난 적과 최대 4인 파티로 Turn Gauge 기반 턴제 전투를 벌이는 오픈월드 파티 RPG**다.

Minecraft는 생존 샌드박스 진행의 대상이 아니라 월드, 이동, 카메라, 엔티티, 렌더링, 멀티플레이를 제공하는 게임 플랫폼이다.

## 2. 이번 대격변에서 유지하는 것

- 최대 4인 파티
- Turn Gauge / SPD 기반 행동 순서
- Gauge 기준 1000과 행동 후 1000 차감, 초과분 보존이라는 개념
- 캐릭터별 Basic / Active / Passive와 개별 전투 역할
- 필드의 가시적 적 조우 → 턴제 전투 → 보상 → 실제 필드 복귀
- 서버 권위 전투/재화/보상/진행
- AUTO와 1x/2x 같은 편의 기능
- 전투 장면 자체를 화면의 주인공으로 두는 방향
- 현재 튜토리얼의 “실제 플레이 중 기능을 순서대로 익히게 하는 방식”

전투를 다른 게임으로 교체하지 않는다. 현재 전투의 좋은 골격을 남기고 계산, 카메라, UI, 캐릭터 설계와 presentation을 보수한다.

## 3. 이번 대격변에서 폐기하는 것

- Aster March / Radia / Southgate / Gloamwood / Aqueduct / Quarry / Old Relay를 production 물리 월드로 쓰는 전제
- 옛 고정 좌표, 고정 도로, authored ribbon, 지형 생성/평탄화/복구 코드
- 옛 좌표에 맞춘 NPC/퀘스트/빠른 이동/카메라 전제
- 임시 제작 셀을 본편 월드처럼 확장하는 방식
- 작은 글씨와 텍스트 카드가 화면을 지배하는 UI
- Minecraft 기본 폰트/버튼을 계획 없이 그대로 쓰는 production UI
- ★1~2를 의도적으로 약한 “재료 캐릭터”로 넣는 구조
- 사용하지 않는 옛 버전 문서/코드를 보존만 하는 관행
- TURNBOUND: RE를 현재 프로젝트의 정본/의존 프로젝트로 취급하는 것

Git history가 과거를 보존한다. production source와 현재 기획에는 현재 게임에 필요한 것만 남긴다.

## 4. 핵심 플레이 루프

```text
마을/거점에서 준비
→ 길과 지형을 직접 탐험
→ NPC/랜드마크/사건/숨은 공간 발견
→ 필드의 적을 발견하고 회피·접근·선제 조건 판단
→ 턴제 전투
→ 경험치·Gold·수집 재화·장비/재료
→ 캐릭터/파티 성장
→ 새로운 지역·던전·강적·스토리 접근
→ 새로운 캐릭터와 파티 조합
→ 더 깊은 탐험
```

게임을 켜는 이유가 메뉴 관리 자체가 되어서는 안 된다. 이동, 발견, 전투, 성장, 새로운 조합이 서로 이어져야 한다.

## 5. 월드 — Drehmal을 실제 게임 공간으로 사용

Production base는 별도로 설치하는 **Drehmal: APOTHEOSIS v2.2.2f**다.

TURNBOUND는 Drehmal을 배경 그림처럼 쓰지 않는다. 이미 존재하는 긴 도로, 마을, 숲, 폐허, 다리, 협곡, 동굴, 던전 입구와 랜드마크를 게임 규칙에 편입한다.

### 5.1 장소를 먼저 읽고 콘텐츠를 배치한다

NPC/조우/퀘스트를 만들기 전에 실제 장소를 조사한다.

각 후보 구간마다 최소한 다음을 기록한다.

- 지형과 높이 차
- 도로/갈림길/막다른길
- 입구와 출구
- 시야가 열리고 닫히는 지점
- 마을/시설의 실제 기능
- 넓은 전투 가능 공간
- 좁은 길/다리/절벽 등 전투 부적합 공간
- 자연스러운 매복/순찰/휴식 지점
- 주변 POI와 이동 시간
- 플레이어가 처음 봤을 때 읽히는 랜드마크
- 카메라 충돌 위험
- 원본 Drehmal 콘텐츠와 충돌할 수 있는 요소

좌표부터 정하고 역할을 끼워 맞추지 않는다.

### 5.2 NPC 배치 규칙

NPC는 “퀘스트 버튼”이 아니라 그 장소에 사는 사람처럼 배치한다.

- 상인: 시장, 여관, 교차로, 교역 거점
- 경비: 성문, 다리, 위험구역 경계, 감시 지점
- 여행자: 주요 도로, 쉼터, 갈림길
- 사냥꾼/채집가: 마을과 야생의 경계, 숲길
- 연구자/탐험가: 유적, 기록실, 특이 지형
- 구조/구호 NPC: 위험지역 직전 안전 공간

중요 NPC는 실루엣, 복장, 애니메이션과 배치로 먼저 알아볼 수 있어야 한다. 머리 위 텍스트만으로 중요도를 전달하지 않는다.

### 5.3 적 조우 배치 규칙

일정 간격으로 몬스터를 길에 뿌리지 않는다.

조우는 지형을 이유로 가진다.

- 순찰대
- 길목 봉쇄
- 폐허 점거
- 야영지
- 다리/협곡 매복
- 둥지/서식지
- 보급대 습격
- 이동 중인 강적
- 던전 입구 수비
- NPC 사건과 연결된 전투

긴 도로에는 안전 구간, 대화/사건, 갈림길, 전투, 보상, 전망/랜드마크, 휴식이 섞여야 한다. 모든 30~60초를 전투로 채우지 않는다.

## 6. 탐험 구조

완전 선형 챕터 복도는 사용하지 않는다.

- 메인 진행은 방향을 제공한다.
- 도로와 랜드마크가 자연스러운 “주 진행축”을 만든다.
- 주변에 선택 던전, 의뢰, 캐릭터 사건, 강적, 상자/발견 요소를 둔다.
- 발견한 장소는 지도/미니맵에 점진적으로 기록한다.
- 미발견 콘텐츠를 처음부터 모두 노출하지 않는다.

Drehmal 원본의 탐험 재미를 훼손하지 않으면서 TURNBOUND의 전투/성장 루프가 그 위에 얹혀야 한다.

## 7. 전투

### 7.1 전투 골격

- 아군 최대 4
- 일반 적 1~5
- 고정 순번제가 아닌 SPD + Turn Gauge
- MP/AP 공통 자원 없음
- Basic은 CD 0
- Active는 주로 쿨타임으로 제한
- 플레이어 선택 중 논리 전투시간 정지
- Reaction은 정규 행동권과 분리
- 서버가 최종 전투 상태를 결정

### 7.2 전투에서 고칠 핵심

- SPD 차이가 실제 행동 빈도와 정확히 연결되어야 한다.
- Gauge 조작 스킬과 SPD 버프/디버프가 같은 scheduler를 사용해야 한다.
- HUD의 행동 예측은 엔진과 같은 계산기를 사용해야 한다.
- 1x/2x는 presentation 속도만 바꾸고 논리 결과는 바꾸지 않는다.
- 쿨타임, Reaction, 부활, 추가 행동의 규칙을 하나의 action economy로 검토한다.

정수 pulse 반올림 때문에 서로 다른 SPD가 같은 행동 주기로 뭉개지는 현재 구현은 새 정본에서 허용하지 않는다.

## 8. 전투 카메라

카메라의 기준은 Minecraft Player가 아니라 **현재 전투의 중심**이다.

전투 시작 시:

1. 실제 지형에서 안전한 battle footprint를 찾는다.
2. 아군/적 formation anchor를 지형 높이에 맞춘다.
3. 양측 formation centroid를 계산한다.
4. 두 centroid 사이의 중심을 battle center로 정한다.
5. 카메라는 battle center를 바라보며 전체 전투원을 프레임에 넣는다.

스킬 연출이 잠깐 actor/target 쪽으로 이동할 수는 있지만 연출 종료 후 battle center 기준으로 자연스럽게 복귀한다.

카메라는 언덕, 벽, 절벽, 좁은 길에서:
- 충돌을 피하고
- 전투원을 지형 뒤에 숨기지 않으며
- 필요한 경우 거리/높이/좌우 각도를 자동 보정하고
- 특정 월드 좌표나 한 방향을 전제로 하지 않는다.

## 9. 전투 UI

전투 장면이 가장 중요하다.

기본 정보 계층:

1. 실제 3D 아군/적
2. 현재 행동자와 선택 대상
3. 다음 행동 순서
4. 현재 캐릭터의 행동/스킬
5. 파티 HP/상태
6. AUTO/배속/도주 같은 보조 조작

캐릭터 얼굴/머리 portrait가 품질 좋게 확보되면 같은 icon atlas를:
- 파티 편성
- 전투 파티 HUD
- Turn Order rail
- 캐릭터 상세
- 전투 결과
에 공용한다.

실제 캐릭터 모델/텍스처에서 안정적으로 얼굴을 뽑을 수 없거나 라이선스가 허용하지 않으면 저품질 자동 crop을 강행하지 않는다.

## 10. 튜토리얼

별도 설명방에서 긴 텍스트를 읽히지 않는다.

Drehmal의 실제 초반 동선 안에서:
- 이동/상호작용
- NPC 대화
- 첫 가시적 조우
- Basic
- 타깃 선택
- Active/CD
- Turn Order와 SPD
- 파티 관리
- 보상/성장
- AUTO/2x
를 순서대로 실제 행동으로 익힌다.

이미 아는 기능을 반복해서 막거나 확인시키지 않는다. 튜토리얼 메시지는 짧고, 언제든 다시 볼 수 있는 도움말은 별도로 제공한다.

## 11. 캐릭터 수집과 성장

캐릭터는 숫자 차이가 아니라 **전투 규칙을 다르게 쓰게 만드는 선택지**여야 한다.

모든 정식 수집 캐릭터는:
- 한 문장으로 설명 가능한 역할
- 눈에 보이는 signature mechanic
- 강한 조합 1개 이상
- 실제 약점 1개 이상
- 3D로 읽히는 실루엣/무기/행동
을 가진다.

낮은 희귀도를 쓰레기/재료로 만들지 않는다. 좁은 역할을 가진 저희귀도 전문가는 가능하지만 “뽑으면 실패”인 캐릭터를 의도적으로 만들지 않는다.

성장 메뉴 수를 늘리는 것보다 레벨, 장비, 최종 각성처럼 역할이 다른 축만 남긴다. 상세 규칙은 Balance 문서를 따른다.

## 12. 소환(가챠)

실제 현금 결제나 기간 한정 FOMO는 사용하지 않는다. 소환은 캐릭터 수집과 파티 실험을 위한 게임 내 보상 루프다.

Presentation은 가능하면 3D를 우선한다.

권장 흐름:

```text
소환 장치/공간 활성
→ 희귀도 사전 신호
→ 실루엣/문양
→ 실제 3D 캐릭터 등장
→ 고유 포즈/짧은 카메라 연출
→ 이름/희귀도/신규 여부
→ 10회 결과 요약
```

- 결과 RNG는 연출 전에 서버에서 확정한다.
- SKIP은 처음부터 가능해야 한다.
- 높은 희귀도는 더 길기만 한 연출보다 다른 소리/구도/빛/등장 방식으로 구분한다.
- 3D 모델을 안정적으로 보여줄 수 없는 캐릭터는 2.5D fallback을 사용할 수 있다.
- 현재 텍스트 카드 중심의 2D reveal은 production 목표가 아니다.

## 13. 미니맵/월드맵

새 미니맵의 목적은 RPG 탐험 지원이다.

표시 후보:
- 현재 도로/지형 윤곽
- 발견한 마을/랜드마크
- 활성 목표
- 이미 만난 중요 NPC/시설
- 빠른 이동 지점
- 발견한 위험구역/보스
- 파티원/멀티플레이어 위치

원칙:
- 미발견 POI를 자동 공개하지 않는다.
- 월드맵과 미니맵은 같은 marker semantics를 공유한다.
- 옛 Aster March fixed image/map data는 재사용하지 않는다.
- Drehmal 지도를 그대로 복제하는 대신 라이선스와 기술 방식이 확인된 데이터만 사용한다.

## 14. UI/UX

UI는 외부 고품질 레퍼런스와 사용 가능한 UI asset을 먼저 고른 뒤 구현한다.

- Minecraft 기본 글꼴에 의존하지 않는다.
- 한국어 가독성을 우선한다.
- 작은 글씨, 잦은 말줄임표, 긴 설명의 상시 노출을 피한다.
- 같은 정보는 한 곳에서 명확하게 보여준다.
- GUI Scale/해상도 변화에 대응한다.
- 상세 설명은 hover/tooltip/상세창으로 보내고 기본 화면은 빠르게 읽히게 한다.
- 자산 경로는 기능별로 얕고 예측 가능하게 유지한다.

세부 디자인 시스템은 `UI_DESIGN_SYSTEM.md`.

## 15. 코드/문서 청결

- 대체가 끝난 obsolete production code는 제거한다.
- deprecated 폴더를 쓰레기통으로 사용하지 않는다.
- 옛 좌표/옛 월드/옛 UI를 새 코드가 참조하지 않는다.
- save/network migration처럼 실제 호환에 필요한 코드는 목적과 제거 조건을 문서화한다.
- 새 정본이 옛 문서를 완전히 대체하면 옛 문서는 Git history에 맡기고 저장소 현재 트리에서 제거한다.
- “혹시 나중에 쓸지 모름”은 유지 이유가 아니다.

## 16. 완성 판단

기능 존재가 아니라 다음이 동시에 만족되어야 한다.

- 이동이 지루하지 않은가
- 전투가 선택을 만든는가
- SPD/Gauge가 실제로 체감되는가
- 캐릭터 역할이 겹치지 않는가
- UI를 한눈에 읽을 수 있는가
- 카메라가 실제 지형에서 안정적인가
- NPC와 적 배치가 장소에 어울리는가
- 캐릭터/적/보스의 외형과 연출이 게임 수준인가
- 성장/재화가 관리 노동이 아닌 다음 선택으로 연결되는가
- 저장/보상/멀티플레이 권위가 안전한가

TURNBOUND의 목표는 “Minecraft 안에서 구현된 시스템 모음”이 아니라 **하나의 완성된 3D 턴제 RPG**다.
