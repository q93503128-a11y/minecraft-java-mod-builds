# TURNBOUND Game Design v1

> TURNBOUND 대격변 이후의 게임 경험 정본.
> 전투 수치/경제는 `02_BALANCE_RULES_v1.md`, 캐릭터별 설계는 `03_CHARACTER_DESIGN_v1.md`, UI는 `UI_DESIGN_SYSTEM.md`, 월드 배치는 `WORLD_OVERHAUL_DREHMAL.md`를 따른다.
> Aster March와 이전 alpha별 임시 설계는 정본이 아니다.

## 1. 게임 정체성

TURNBOUND는 **Minecraft Java의 거대한 3D 판타지 월드를 직접 여행하며 동료를 모으고 성장시키고, 필드에서 만난 적과 최대 4인 파티로 Turn Gauge 기반 턴제 전투를 벌이는 오픈월드 파티 RPG**다.

Minecraft는 생존 샌드박스 진행의 중심이 아니라 월드, 이동, 카메라, 엔티티, 렌더링, 멀티플레이 기반을 제공한다. 플레이어가 느껴야 하는 것은 “마인크래프트에 메뉴를 얹었다”가 아니라 “마인크래프트 공간에서 돌아가는 완성된 3D 파티 RPG”다.

## 2. 핵심 기둥

### 2.1 실제 월드를 걷는 탐험
- 마을과 도로, 숲, 폐허, 협곡, 동굴, 다리, 던전 입구가 실제 플레이 공간이다.
- 메뉴에서 지역을 고르는 것이 아니라 직접 이동한다.
- 긴 길은 이동 노동이 아니라 사건, 조우, 전망, 갈림길, NPC, 휴식이 이어지는 탐험 리듬이 된다.

### 2.2 전투의 중심은 현재 TURNBOUND 전투 골격
- 최대 4인 파티
- SPD + Turn Gauge
- Basic / Active / Passive / Awakening
- 실제 3D 전장
- 서버 권위
- AUTO / 1x / 2x
- 필드 조우 → 전투 → 같은 월드 맥락으로 복귀

전투 자체를 다른 시스템으로 교체하지 않는다. 수치 계산, 행동 경제, 캐릭터 kit, 카메라, UI, 연출을 보수한다.

### 2.3 캐릭터는 다른 규칙을 제공
캐릭터 차이는 공격력 차이가 아니라:
- 누구의 행동을 당기는가
- 누구 대신 맞는가
- 어떤 조건에서 추격하는가
- 어떤 사건을 자원으로 바꾸는가
- 어떤 위험을 감수하는가
처럼 플레이 방식 자체를 바꿔야 한다.

### 2.4 관리보다 선택
새 메뉴, 재화, 강화축을 추가하기 전에 “이것 때문에 새로운 선택이 생기는가?”를 묻는다.
반복 클릭, 중복 재화, 별 의미 없는 장비 세탁, 스킬 레벨업 재료 수집은 기본적으로 넣지 않는다.

## 3. 핵심 루프

```text
거점에서 짧게 준비
→ 실제 길을 따라 탐험
→ NPC/랜드마크/사건/숨은 지형 발견
→ 적을 발견하고 접근·회피·우회 판단
→ 턴제 전투
→ 경험치·Gold·장비·Summon Crystal·탐험 해금
→ 파티/장비/캐릭터 조정
→ 더 위험한 길·던전·보스·캐릭터 사건
→ 새로운 파티 조합
→ 더 깊은 탐험
```

메뉴에 머무는 시간보다 월드와 전투에 머무는 시간이 길어야 한다.

## 4. 플레이 세션 리듬

### 4.1 짧은 15분 세션
- 길 한 구간 탐험
- 2~4번의 의미 있는 조우
- NPC 사건 1개 또는 소형 POI 1개
- 장비/Gold/Crystal 중 최소 하나의 눈에 보이는 성장

### 4.2 30~60분 세션
- 거점 → 도로 → 목적지 한 묶음
- 선택 경로 1개 이상
- Elite 또는 소형 던전
- 캐릭터/장비/지도 상태에서 실제 변화

### 4.3 긴 세션
- 새 지역 진입
- 지역의 주요 NPC/문제 파악
- 던전/보스
- 새로운 캐릭터, 빠른 이동, 상점, 소환권 같은 큰 해금

진행을 “매 5분마다 팝업 보상”으로 만들지 않는다. 탐험 결과가 보상이 되게 한다.

## 5. Drehmal을 실제 게임 월드로 사용

Production world는 별도 설치되는 **Drehmal: APOTHEOSIS v2.2.2f**다.

TURNBOUND는 Drehmal 위에 Aster March를 다시 만들지 않는다.

### 5.1 금지
- 대규모 평탄화
- TURNBOUND 전용 인공 대로
- 옛 Aster 구조물 복원
- 고정 평지 전투장 permanent 생성
- 기존 장소를 무시하고 좌표만 찍은 NPC/적
- 원본 지도 이미지를 허가 없이 게임 자산으로 복제

### 5.2 허용
- 기존 장소에 gameplay 의미 부여
- NPC/적/상호작용 배치
- 비파괴 marker
- runtime battle formation
- discovery/quest state
- 별도 TURNBOUND save metadata

## 6. 월드 배치의 기본 원칙

### 6.1 장소가 먼저, 역할이 나중
순서는 반드시:
1. 실제 장소 관찰
2. 이동 동선 관찰
3. 카메라/전투 가능성 확인
4. 그 장소가 무엇에 적합한지 결정
5. NPC/조우/퀘스트 역할 부여

“상인이 필요하니 x=500에 상인” 같은 방식은 금지한다.

### 6.2 긴 길의 리듬
표준 길은 다음 패턴을 반복하되 기계적으로 배치하지 않는다.

```text
안전한 이동
→ 시야 변화/랜드마크
→ NPC/사건/갈림길
→ 적 조우 또는 회피 선택
→ 짧은 회복 구간
→ 보상/목적지
```

표준 노선에서 **강제 전투가 30~60초마다 반복되지 않게** 한다.
큰 의미 없는 빈 길도 피한다.

### 6.3 배치 밀도 목표
지형에 따라 유동적이지만 첫 설계 기준:
- 주요 거점 내부: 의미 있는 기능 NPC 3~6명 + 분위기 NPC 소규모
- 일반 도로: 45~90초 이동마다 “무언가 읽히는 변화”
- 필수 전투: 보통 2~3분에 1회 이하
- 위험 도로/던전 접근: 1~2분에 1회 수준 가능
- Elite/강적: 미리 읽히고 우회할 수 있는 경우가 많아야 함

숫자를 맞추기 위해 빈 공간에 NPC를 세우지 않는다.

Capital Valley 첫 route의 1차 밀도는 **일반 필드 그룹 6개 + 선택 Elite 1개 + 길 위 NPC 3명**을 기준으로 한다.
이는 전투를 일정 간격으로 뿌리는 규칙이 아니라 첫 실제 노선의 콘텐츠 밀도 출발점이며,
실제 지형/시야/우회 가능성에 따라 일부 조우는 비활성될 수 있다.

## 7. NPC 설계

NPC는 좌표에 박힌 메뉴 버튼이 아니다.

### 7.1 역할 유형
- 서비스: 상인, 여관, 장비/정비
- 진행: 스토리, 던전, 지역 문제
- 세계: 여행자, 경비, 사냥꾼, 연구자, 주민
- 사건: 매복 피해자, 구조 요청, 호위 대상
- 캐릭터: 영입/개인 스토리/각성 퀘스트

### 7.2 위치 논리
- 상인: 시장, 여관, 교차로, 교역 거점
- 경비: 성문, 다리, 감시 지점, 위험 구역 경계
- 여행자: 큰 도로, 쉼터, 갈림길
- 사냥꾼: 마을과 야생 경계
- 연구자: 유적/기록 공간
- 구조 NPC: 위험 지역 바로 직전의 안전 구역

### 7.3 NPC가 살아 보이게
중요 NPC는:
- 역할에 맞는 모델/복장
- 짧은 idle/시선/손동작
- 필요 시 작은 이동 반경
- 낮/밤 또는 진행 상태에 따른 최소한의 위치 변화
를 고려한다.

모든 NPC를 제자리 정지 상태로 만들지 않는다.

## 8. 필드 조우 설계

몬스터를 도로에 일정 간격으로 뿌리지 않는다.

조우 archetype:
- 순찰
- 매복
- 길목 봉쇄
- 폐허 점거
- 야영지
- 둥지/서식지
- 보급대 습격
- 이동 중인 강적
- 던전 입구 수비
- NPC 사건 연계

### 8.1 시각적 사전 정보
플레이어가 적을 보기 전에:
- 소리
- 흔적
- 캠프
- 부서진 물체
- 경비 NPC 경고
- 시야에 들어오는 실루엣
같은 정보가 있을 수 있다.

“보이지 않는 trigger를 밟자마자 전투”는 특별한 매복을 제외하고 남발하지 않는다.

### 8.2 회피
필드전은 모든 경우 강제가 아니다.
- 우회
- 거리 벌리기
- 다른 길
- 높은 난이도 적 회피
가 가능해야 탐험이 살아난다.

## 9. 전투

### 9.1 불변 골격
- 아군 최대 4
- 적 보통 1~4, 일반 상한 5
- Turn Gauge 1000
- 행동 후 1000 차감, overflow 보존
- 플레이어 선택 중 논리 시간 정지
- Basic CD 0
- Active는 주로 cooldown
- Reaction은 정규 행동권과 분리
- 1x/2x는 presentation만 변화
- 서버 권위

### 9.2 v1 핵심 보수
- 정수 pulse 양자화 폐기
- fixed-point TurnScheduler 사용
- 실제 다음 actor / HUD order / AUTO가 같은 scheduler 사용
- SPD는 실제 행동 빈도
- Gauge 조작은 action economy
- 스킬/패시브의 무료 추가 행동 가치를 별도 계산

## 10. 전투 카메라

카메라의 기준점은 플레이어가 아니라 **battle center**다.

### 10.1 시작
1. 조우 근처 battle candidate 탐색
2. 아군/적 formation anchor 계산
3. 두 진형 centroid 계산
4. battle center 결정
5. 모든 전투원이 프레임에 들어오는 3/4 시점 선택

### 10.2 기본 카메라
- **카메라의 실제 pivot/주시는 두 진형 centroid의 중점**이어야 한다.
- Minecraft Player shell을 pivot으로 둔 채 yaw/pitch만 전투장 쪽으로 돌리는 방식은 금지한다.
- 마우스 orbit/휠 zoom도 플레이어 몸이 아니라 이 battle-center pivot을 기준으로 돈다.
- 화면 중앙은 두 진형 사이
- UI가 전투원 얼굴/실루엣을 가리지 않음
- 4v5에서도 전원 식별
- 캐릭터 키/크기가 달라도 자동 거리 보정

### 10.3 스킬 카메라
- Basic: 기본 카메라 유지 또는 아주 짧은 actor emphasis
- 일반 Active: actor→target 방향의 짧은 이동
- Signature/Awakening급 연출: 더 큰 camera move 허용
- 연출 종료: 반드시 battle-center view 복귀

### 10.4 충돌 fallback
벽/절벽/나무 때문에 원 시점이 불가능하면:
1. 뒤로 이동
2. 높이 상승
3. 반대측 3/4 angle
4. 마지막으로 높은 overhead 3/4

벽을 관통하거나 바닥 안으로 들어가는 카메라는 허용하지 않는다.

### 10.5 종료
전투 전 player camera/mode/state를 저장하고 확실하게 복구한다.
전투 중 disconnect/death/forced end도 같은 복구 경로를 사용한다.

## 11. 전투 UI

3D 전장이 화면의 주인공이다.

권장 공간:
- 상단: Turn Order rail
- 하단 좌측: 파티 portrait + HP/상태
- 하단 우측: 현재 actor 행동/스킬
- 작은 보조 strip: AUTO / 1x·2x / 도주
- 적 HP/상태: 실제 적과 공간적으로 연결

### 11.1 Turn Order
가능하면 캐릭터 얼굴 portrait 사용.
- 현재 행동자
- 다음 6~10 행동
- 연속 행동은 portrait 반복
- Gauge 변화 즉시 반영
- hover/focus에서 SPD/Gauge 상세

### 11.2 스킬
기본 버튼:
- icon
- 이름
- cooldown
- target hint

긴 설명은 tooltip/detail로 이동.
말줄임표로 핵심 효과를 숨기지 않는다.

### 11.3 portrait
최종 3D 모델에서 품질 좋은 얼굴 렌더를 만들 수 있으면:
- 파티창
- 전투 HUD
- Turn Order
- 캐릭터 상세
- 결과 화면
- 소환 결과
에 같은 portrait를 쓴다.

품질이 나쁘거나 라이선스가 불명확하면 억지 자동 crop을 쓰지 않는다.

## 12. 캐릭터 수집

태생 희귀도는 **★1~★5**를 사용한다.

- ★1~★2: 소재형/저성능 저희귀도 캐릭터. 단순한 kit와 낮은 전투 ceiling을 허용하지만 실제 캐릭터/소환 풀에서 삭제하지 않는다.
- ★3: 단순하고 좁은 전문성
- ★4: 완성된 signature loop
- ★5: 더 높은 ceiling/선택지
- 높은 태생 성급이 낮은 성급의 모든 역할을 수치로만 압도해서는 안 된다.

초기 저희귀도 캐릭터:
- F01 민병 견습생 ★1
- F02 야전 견습생 ★1
- F03 변경 사냥꾼 ★2
- F04 방패 용병 ★2

P01~P08은 핵심 영웅 로스터이며, F01~F04를 legacy-only/NPC-only로 밀어내지 않는다.

초기 4인 파티는 스토리로 확보할 수 있게 하고, 소환은 파티 다양성과 수집을 확장한다. 메인 진행에 특정 가챠 캐릭터를 요구하지 않는다.

## 13. 성장

주 성장축:
- 기본 XP Level 1~60
- 중복 전용 +Level 0~10 — 기본 레벨과 합산해 실질 최대 Lv70
- Equipment 3 slots
- Signature 1 slot
- Awakening 1회

+Level 규칙:
- 같은 캐릭터 중복 1회당 +1
- 기본 레벨이 60이 아니어도 즉시 적용
- 전투/퀘스트 XP와 별도
- 최대 +10
- 중복 Star Essence 보상과 동시에 지급
- +10 이후에도 Essence 보상은 유지
- 수치 성장축이며 스킬/패시브/별 승급을 중복에 잠그지 않음

삭제/비채택:
- 별도 스킬 레벨업 재료
- 장비 실패 강화
- 무작위 부옵 리롤
- 여러 종류의 승급석
- 매일 해야 하는 성장 일일 숙제

Awakening은 캐릭터 개인 사건/퀘스트와 연결한다. 별도 “각성 코어” 재화를 장기 정본으로 두지 않는다.

2026-09-29 독립 감사에서 과거 `nativeStar`/`currentStar`, 성장으로 ★6, 각성과의 선행 관계가 존재했던 이력은 확인됐다. 그러나 현재 Drehmal/v1 구조에 어떤 관계를 채택할지는 아직 사용자 결정 사항이다.
결정 전에는 v0.4 승급 체계를 자동 부활시키거나 `currentStar` 저장 필드를 삭제하지 않으며, 현재 Lv1~60/장비/Awakening 개편도 통째로 되돌리지 않는다.

## 16. 튜토리얼

현재의 “실제 플레이 중 하나씩 배우는 방식”은 유지한다.

첫 route의 실제 공간 정본은 `FIRST_ROUTE_CAPITAL_VALLEY_v1.md`.

시작 위치는 Drabyel 내부나 원본 Stasis pod가 아니라 **Stasis 지상 출구 직후 Capital Valley 기존 길의 안전한 roadhead**로 한다. 이 결정은 원본 Stasis 스토리 강제 없이 첫 world reveal과 Drabyel 도착감을 모두 살리기 위한 것이다. 정확한 블록은 26.2 지형 검수 후 고정한다.

### 단계
1. 이동/상호작용
2. 첫 NPC
3. 첫 가시적 조우
4. Basic / 타깃
5. Active / cooldown
6. Turn Order / SPD / Gauge
7. 파티 화면
8. 장비

이미 수행한 행동은 다시 강제하지 않는다.
도움말은 나중에 다시 볼 수 있다.

### 월드맵

## 18. 빠른 이동

빠른 이동의 목적은 **처음 가는 길을 생략하는 것**이 아니라, 이미 탐험한 장거리 왕복을 반복 노동으로 만들지 않는 것이다.

핵심 원칙은 **“처음 가는 길은 모험, 이미 간 길은 편의”**다.

- 탈것과 빠른 이동은 다른 역할이다.
  - 탈것: 탐험 중 단·중거리 이동을 빠르게 하면서 적/NPC/샛길/POI를 계속 만나는 수단.
  - 빠른 이동: 이미 발견한 지역 사이의 장거리 재방문 수단.
- 모든 장소를 순간이동 메뉴로 만들지 않는다.
- 큰 거점, 지역의 대표 랜드마크, 명확한 travel node만 빠른 이동 지점이 된다.
- 해당 지점을 플레이어가 **직접 한 번 방문해야 영구 해금**된다.
- 미발견 빠른 이동 지점은 이동 대상으로 사용할 수 없다.
- 전투 중이거나 필드 적에게 실제로 추격당하는 중에는 사용할 수 없다.
- 던전 내부/전투 구역 안에서 탈출 버튼처럼 사용하는 빠른 이동은 두지 않는다.
- 이동 비용을 반복 Gold 소모로 강제하지 않는다. 기본 빠른 이동은 무료 편의 기능이다.
- 도착 위치는 서버가 현재 지형의 충돌/유체/머리 공간을 다시 검사해 안전한 지면으로 결정한다.
- 멀티플레이에서도 각 플레이어의 발견 상태와 이동 요청은 서버가 판정한다.
- 월드맵에서는 **발견 완료된 빠른 이동 거점만 활성 표식**으로 표시하고 직접 선택해 이동할 수 있다.

첫 Capital Valley 노선은 거리를 충분히 벌린 세 지점만 사용한다.

1. **프라이멀 길머리** — 첫 여정 시작부로 돌아오는 동쪽 거점.
2. **Capital Valley Tower** — 지역 중앙의 대표 랜드마크.
3. **New Drabyel** — 첫 대형 안전 거점.

Explorer Camp, Warning Cave 같은 중간 POI는 목적지 가치가 있어도 빠른 이동 지점으로 만들지 않는다.
그래야 첫 탐험과 도로의 적/NPC/사건이 계속 의미를 가진다.

이후 지역도 같은 원칙으로 확장하며, travel node 사이를 너무 촘촘하게 배치하지 않는다.

## 19. 퀘스트

퀘스트는 “가서 10마리 잡기” 목록이 아니라 장소와 사건을 연결한다.

플레이어-facing 분류:
- **메인 목표**: 현재 이야기/지역 진행의 주축. HUD에서 항상 최우선.
- **서브 목표**: 지역 NPC, 구조, 탐사, 선택 Elite, 숨은 POI처럼 한 번 해결하는 선택형 사건.
- **캐릭터 목표**: 개인 이야기, 각성, 전용 장비 시련.
- **지역 의뢰**: 반복 가능한 선택형 계약. 일일 출석/연속 보상/FOMO 없이 필요할 때 수행.
- **도전**: 특수 전투 조건, 기록, 장기 목표. 일반 퀘스트 동선과 분리.

HUD:
- 메인 1개 + 추적한 보조 목표 최대 2개.
- 접힌 HUD는 메인 목표를 우선하고 보조 목표는 짧게 표시.
- 상세 화면에서 서브/지역 의뢰를 추적/해제.
- 반복 의뢰는 메인 진행 필수가 아니며 성장 효율 때문에 매일 해야 하는 숙제가 되면 실패다.

좋은 예:
- Warning Cave 강적 조사
- Drabyel 분실 화물 회수
- Av'Sal 외곽 순찰대 제거
- 특정 도로 안전 확보
- 발견한 캠프/유적 조사

피할 것:
- 의미 없는 일반 몬스터 N마리 반복
- 같은 길 왕복 배달
- daily streak
- 랜덤 목표를 대량 생성해 지도에 마커를 뿌리는 방식

## 22. UI / 외부 디자인

외부 고품질 UI/asset을 우선한다.

### 21.1 임시 플레이어-facing 디자인 금지

플레이어가 실제로 보게 되는 UI, 모델, 텍스처, 아이콘, 초상화, VFX 외형은
**“일단 임시로 만들고 나중에 교체”하는 방식으로 구현하지 않는다.**

첫 visible implementation부터 다음 중 하나를 사용한다.

1. 라이선스와 출처가 확인된 `direct_asset`
2. 수정 사용이 가능한 `editable_base`
3. 검증된 외부 디자인을 기준으로 만든 final-quality original asset

적절한 자산이 아직 없으면 임의의 AI 임시 디자인, 바닐라 대체 외형, 검정 패널, placeholder icon/model을
normal gameplay에 먼저 넣는 대신 **시각 binding을 보류하고 자산을 먼저 확보한다.**

예외는 플레이어에게 노출되지 않고 production runtime에서 비활성인 내부 로직/검증용 scaffold뿐이다.
이 예외를 normal gameplay의 임시 외형으로 확대하지 않는다.

- reference / editable base / direct asset / code library / unknown-license 구분
- unknown-license bytes는 vendoring 금지
- 외부 asset은 SOURCE/LICENSE 추적
- 한 화면에서 무계획하게 여러 UI pack 혼합 금지
- Minecraft 기본 버튼/글꼴을 production 기준으로 삼지 않음

## 20. 멀티플레이

정본은 `MULTIPLAYER_DESIGN_v1.md`를 따른다.

- 플레이어 파티와 캐릭터 4인 파티는 다른 개념.
- 플레이어 파티 최대 4명.
- 필드 탐험, 위치/미니맵, 조우 claim, 향후 co-op 전투의 social unit.
- 다른 플레이어가 전투 중이면 실제 전투 캐릭터/애니메이션은 같은 월드에서 보이게 한다.
- target/focus 같은 개인 UI marker만 owner-private.
- PvP는 강제 오픈월드 공격이 아니라 상호 동의 duel/ranked 전용 전투.
- damage/action/reward/ranking/quest credit은 서버 권위.
- 기존 single-owner BattleSession에 조건문을 누적하지 않고 shared/multi-owner session을 별도 설계.
- Co-op PvE의 적 HP는 참가 플레이어 수만큼 선형 배율: 1p x1 / 2p x2 / 3p x3 / 4p x4.
- 1인은 기존 1열 배치. 2인 이상은 플레이어별 4캐릭터를 2x2 블록으로 묶고 블록들을 좌우로 나열한다.
- 2x2의 앞/뒤 행은 시각적 정리일 뿐 전투 규칙상 차이가 없다.

## 25. 완성 기준

TURNBOUND는 다음이 동시에 맞아야 한다.

- 걷는 시간이 지루하지 않음
- 조우가 장소에 어울림
- 전투에서 실제 선택이 생김
- SPD/Gauge가 체감됨
- 캐릭터 역할이 겹치지 않음
- UI가 즉시 읽힘
- 카메라가 지형에서 안정적
- NPC가 장소에 자연스럽게 존재
- 성장/재화가 관리 노동이 아님
- 모델/애니메이션/VFX/SFX 품질이 전투 중요도에 맞음
- 서버 권위/저장/보상 안정성 유지
- 실제 플레이에서 재미와 편의가 확인됨

목표는 구현률 100%가 아니라 **완성된 하나의 게임**이다.
